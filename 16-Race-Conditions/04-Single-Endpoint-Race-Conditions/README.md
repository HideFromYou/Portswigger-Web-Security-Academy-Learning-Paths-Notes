# Single-Endpoint Race Conditions

## Overview

In a single-endpoint race condition, parallel requests are sent to the same endpoint with different parameter values.

The requests race to write to shared state, such as session variables or database fields, that is not updated atomically.

## How It Works

Request 1:  change-email with value A
Request 2:  change-email with value B

If the application stores the value first and later reads it again to perform the next step, a second request can change the stored value in between.

The step that follows then uses the wrong value.

## Example

An endpoint that changes the email address stores a pending email and then sends a confirmation message.

If the confirmation email is generated by reading the pending email from the database again, the value may already have been replaced by a second parallel request.

The confirmation message and the pending value then belong to different requests.

## Practical Lab

Lab: Single-endpoint race conditions

The vulnerable endpoint was `/my-account/change-email`.

The confirmation email was generated by re-reading the pending email value from the database. A second parallel request could change that value before the email was sent.

The attack:

1. Send two requests to the endpoint in parallel with different email addresses.
2. One request used an address controlled by the attacker.
3. The other request used `carlos@ginandjuice.shop`.
4. The confirmation link for the `carlos@ginandjuice.shop` claim was delivered to the attacker-controlled inbox.
5. Following the link confirmed the address and gave an admin account.

Status: Solved

## Testing Process

1. Find an endpoint that stores a value and uses it in a later step.
2. Send the request sequentially first and record the normal behavior.
3. Send two requests with different values in parallel.
4. Check whether the later step used the wrong value, for example the content of an email.
5. Repeat until the result is consistent.

## Key Takeaway

Reading a value again after it was stored is dangerous when another request can change it in between.

Parallel requests to the same endpoint can break assumptions about state that is not updated atomically.
